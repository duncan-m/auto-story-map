# Story map instructions

Treat [product/story-map.yaml](product/story-map.yaml) as the source of truth for story placement, release grouping and delivery status. Follow [the story map guide](docs/story-map.md) for audience rules, examples and validation.

## Populate the first map

When setting up Auto Story Map in a host product, or when asked to initialise the map, check whether `product/story-map.yaml` is missing, still contains the builder estimates demo, or is the starter map from `story-map init`. Follow the [first-run workflow](docs/story-map.md#populate-the-first-map) to inspect the host product, draft its initial internal map, and validate it. If the product already has a map, keep its story IDs and update only the requested scope.

Use an existing Markdown heading for each engineering overview you can verify. If you are updating a host that already uses the library, follow the [upgrade steps](docs/story-map.md#upgrade-to-077).

## Maintain an existing map

When a change affects a user journey, story scope, release assignment or delivery status, update the map in the same PR. Find existing IDs before creating stories, with `story-map stories --query <text> --status all` and `story-map story <ID>`, and reference those IDs in the delivery plan. When your team runs several agents on one map and claims stories, claim a story with `story-map claim <ID> --agent <name>` before you start it, and pick another story if it exits 3. See [Coordinate several agents](docs/story-map.md#coordinate-several-agents). Name the merged or shipped stories the work builds on and any planned stories it overlaps, and link their plans, so reviewers can see what is new. In this repository, give each new story the lowest free number from ESM-123 upwards, passing it to `story-map add` with `--id`, such as `--id ESM-123`, and skip any number already in the map, cut stories included. Do not let `add` choose the ID here: its next number follows ESM-912, which was issued out of sequence. Never renumber an existing story. Make the smallest map change that matches the agreed work. Prefer `story-map edit`, `add` and `release-impact` to editing the YAML by hand, and check the dry run before adding `--write`. The status history credits the commit author with each edit, or whoever merged it when the author is a bot. Set `updatedBy` only when neither is the person to credit, such as when you make an edit on someone else’s behalf, and use their display name.

When a plan adds or changes UI, include a `## UI mockup` section with an HTML mockup built on the real `styles.css` and board markup, using stories from this map, and a PNG of it, as the existing plans in `docs/plans/` do. When a plan has a mockup, screenshot or design, add its link to the `sources` of each story it shows, after the story’s plan section, and name it in the release `notes` when it covers the release. See [Link mockups and designs](docs/story-map.md#link-mockups-and-designs). Read a story’s `sources` to find its plan, mockups and other material before changing it.

Keep new stories internal by default. Add customer-facing copy only when the story is approved for that audience. Mark a story as `merged` when its work reaches the default branch, and as `shipped` when it is available to its intended users. If the product deploys every merge straight away, go straight to `shipped`. When work stops or is dropped, set the status to `blocked` or `cut` instead of deleting the story, and explain why in `statusReason`. If release assignment or availability is unclear, keep the existing value and flag the question in the PR.

Record each release’s notes and expected impact in its `notes` and `impact`, following [Release notes and impact](docs/story-map.md#release-notes-and-impact). Mark impact items you draft with `draft: true`. Only a person removes `draft`, so never remove it yourself, and never run `story-map confirm` with `--write`. The board cannot edit these fields, so update them in a PR like any other map change.

Tag each story you add or change with the jobs to be done it serves, using the existing job IDs in the map's `personas`, following [Personas and jobs to be done](docs/story-map.md#personas-and-jobs-to-be-done). Never invent a persona or job without marking each job `draft: true` and saying so in the PR, and never remove `draft` yourself.

To find outstanding map work, run `story-map actions`, which lists what the board's Actions tab shows, following [See what the map is waiting for](docs/story-map.md#see-what-the-map-is-waiting-for). You may act on actions that do not need a person. Leave the ones marked as needing a person, such as drafts to confirm and estimates to agree, to a person, and mention them in the PR if your work touches them.

A story's `estimate` is the team's agreed size in story points, following [Estimate effort](docs/story-map.md#estimate-effort). Do not set or change an estimate unless the team has agreed it. When a planned or in-progress story has none, flag it in the PR instead.

When you open the pull request that finishes a story, the one that marks it `merged`, record the tokens used to deliver it and their estimated cost, following [Record the tokens used on a story](docs/story-map.md#record-the-tokens-used-on-a-story). In Claude Code, run `story-map tokens <ID>`, adding `--branch` for a branch your session started on before you renamed it, record them with `story-map edit <ID> --tokens <n> --estimated-cost <usd>`, and paste the output of `story-map tokens --format markdown <ID>` into the PR's **Tokens used** section. Other agents record the count and cost their own tool reports. When you cannot count them, say so in that section instead of guessing.

When you add or change a test that covers a story, put the story ID at the start of the test's name, followed by a colon, such as `test("ESM-702: exports a valid Visio package", …)`. See [Link tests to stories](docs/story-map.md#link-tests-to-stories).

Run `npm run validate` in this source repo. It also checks sources and the story IDs in `docs/`. In a product that installs the package, run `npx --no-install story-map validate product/story-map.yaml`. Add `--check-sources` to check that sources and `#heading` links exist, and `--tests <folder>` to check the story IDs in test names. Use the same validation in CI, adding `--format github` so problems appear on the PR diff. In the PR description, include the summary from `story-map diff origin/<base branch>` and call out any customer-facing changes. If you cannot run validation, the tests or `story-map diff`, such as when you work without a checkout of the repository, open the PR as a draft, say which commands did not run, and do not write a summary of your own in place of the diff. Someone must run them before the PR is ready for review.

## Branches and pull requests

Give each branch a short, descriptive name that says what the work is, such as `fix/history-name-length` or `docs/review-fixes-plan`. Include the story ID when there is one, such as `fix/esm-601-history-name-length`. Do not use random or generated names, such as `claude/zealous-fermat-srf6a2`, because nobody can tell from the name what the branch holds.

This rule is the repository owner's explicit permission to create and push to a descriptive branch instead of a branch your session assigned, such as `claude/<adjective>-<name>-<suffix>`. Rename the branch before the first push, for example with `git branch -m fix/esm-601-history-name-length`. If you have already pushed the assigned branch, push the descriptive one and open the PR from it.

Title each pull request by what it changes, in plain words, such as “Limit author names in the history file”. Start with the story ID and a colon when there is one, such as “ESM-601: Limit author names in the history file”, or with the range when the PR covers several stories, such as “ESM-130–ESM-138: Plan Git-native delivery metrics”. Name the story IDs in commit messages too, so the story panel's **Changes** section finds the work. Do not use the branch name or a generated phrase as the title. Fill in the sections of [the pull request template](.github/pull_request_template.md).

CI fails a pull request whose branch or title looks generated. Rename the branch or edit the title rather than working around the check.
