## 1. Publish without running dependency scripts

**Problem.** The `publish` job in `.github/workflows/release.yml` has `id-token: write` and runs `npm ci` with install scripts turned on. Every step in the job can ask GitHub for an OpenID Connect token. A compromised dependency's install script could use that token to publish a malicious version through trusted publishing, and the version would get a valid provenance statement. The `contents: write` token is only given to the last step, so that part is already fine.

**Change.**

1. Build and pack once, in a job that has no publishing permissions:
   - Add a `pack` job after `check`, with `permissions: contents: read`. It runs `npm ci`, `npm run build`, `npm pack`, and uploads the `.tgz` with `actions/upload-artifact`, pinned to a commit SHA like the other actions.
2. Make `publish` install nothing:
   - Download the artifact, then run `npm publish ./embedded-story-map-<version>.tgz --provenance --access public`. Publishing a tarball does not run `prepare` or any dependency scripts.
   - Keep the tag and changelog checks. They only need `node -p` and `grep`, and they read `package.json` from the checkout.
   - Drop `cache: npm` from `publish`, since it no longer installs anything.
3. Check that the tarball's `package.json` version matches the tag before publishing, so the artifact cannot drift from the checked tag.
4. In `check` and `pack`, use `npm ci --ignore-scripts` followed by an explicit `npm run build`, so even unprivileged jobs do not run dependency scripts.

**Tests.** Push a tag such as `v0.5.1-rc.0` to a fork, or run the workflow with `workflow_dispatch` against a dry run (`npm publish --dry-run`), and check that the publish job logs show no `npm ci` and that the published file list matches `npm pack --dry-run`.

**Docs.** Update `docs/releasing.md` to describe the pack and publish split, and to say why the publish job must never install dependencies.

## 2. History names that fit the history format

Story: ESM-601.

**Problem.** `storyMapHistorySchema` limits `by` and `mergedBy` to 120 characters, but Git author and committer names have no limit. A 130-character author name produced a history file that `parseStoryMapHistory` rejects, so the host's build or page fails. This happened because the writer (`src/history-git.ts`) and the reader (`src/history.ts`) each describe the format separately.

**Change.**

1. Export one constant, `historyNameMaxLength = 120`, from `src/history.ts` and use it in the schema.
2. In `buildStoryMapHistory`, pass every name through a `historyName(name)` helper before storing it:
   - trim it, and drop it if it is empty,
   - truncate by Unicode code points, not UTF-16 units, so emoji are never split, ending with `…` within the limit.
3. Apply it to `by`, `mergedBy` and `lastEdits[].by`, including names from `updatedBy` (already limited to 120 by the map schema, so this is a no-op there).
4. Stop the two descriptions drifting: keep the documented interfaces in `src/history.ts`, and add a compile-time check that `z.infer<typeof storyMapHistorySchema>` and `StoryMapHistory` are the same type. `tsc` then fails if either changes without the other.
5. Also limit `reason` to 500 characters in the writer, matching both schemas, in case the limits ever differ.

**Tests.**

- A commit by a 130-character author produces a history that `parseStoryMapHistory` accepts, with `by` at 120 code points ending in `…`.
- A name made of emoji is truncated without a lone surrogate.
- A round-trip test: every history the existing Git tests build passes `parseStoryMapHistory`. Add this to the shared test helper so every future history test checks it.

**Docs.** None beyond the changelog entry ("Fixed: very long Git names no longer make the history file invalid").

## 3. History and diff that survive format changes

Story: ESM-602.

**Problem.** `buildStoryMapHistory` parses every past version of the map with today's strict schema and silently skips any version that fails. So far every format change has only added fields, so nothing is lost. But the first time a release removes or renames a field, or removes a status, every older version stops validating:

- their events disappear,
- every story looks newly added at the first version that does validate,
- in-progress dates, the stalled flag and the "Changed in" filter become wrong,

and nothing says so. In the same situation, `story-map diff` stops with an error because the base branch's map is not valid, so hosts' CI fails until the upgrade PR merges.

**Change.**

1. **A lenient parser for past versions.** Add `loadHistoricalStoryMap(source)` in `src/schema.ts`. It is not exported from the package index.
   - Same YAML safety settings as `loadStoryMap`: unique keys and `maxAliasCount: 20`.
   - Builds the schema from the same field definitions with a `strict` switch, so there is still only one description of the format. In lenient mode, unknown keys are dropped instead of failing.
   - Parses each story on its own. A story that still fails, such as one with a status this version no longer knows, is dropped and counted, rather than failing the whole version.
   - Skips the cross-reference checks, which matter for editing, not for reading history.
   - Returns `{ map, dropped: { stories: number, fields: number } }`.
2. **A migration step.** Add `migrateStoryMap(data)` that runs before validation in both parsers. It does nothing today (the format is `version: 1`). It is the place to put a rename or status mapping the next time the format changes, so old versions keep their meaning rather than just being dropped.
3. **History uses it and says what it skipped.**
   - `buildStoryMapHistory` uses `loadHistoricalStoryMap`, and only skips a version when the YAML itself cannot be read or the map file is missing.
   - Add an optional `skipped` field to the history format: `{ commit, reason }` for each skipped version, at most 100 entries, plus `skippedCount`. Both are optional, so older history files still parse.
   - The CLI prints `warning: skipped N versions of the map that could not be read` with the first few commits, to stderr, and still exits 0.
   - The board's history note (internal only) shows "partial" when `complete` is false or anything was skipped.
4. **Diff uses it for the base version only.** `readMapAt` in `src/cli.ts` uses `loadHistoricalStoryMap` for the base ref. The current map is still checked strictly. When anything was dropped from the base, the summary starts with a note: "The map on `<base>` uses an older format. N stories could not be compared." The exit code stays 0, so upgrading the library does not fail CI.

**Tests.**

- A repository whose first commits use an unknown field and later commits do not: history keeps the early `added` events, and their dates are the original commit dates.
- A version with an unknown status: only that story is dropped from that version, and `skippedCount` stays 0.
- A version that is not valid YAML: it is listed in `skipped`, and the CLI warning names its commit.
- `story-map diff` against a base with an unknown field prints the note and exits 0.
- `parseStoryMapHistory` accepts files with and without the new fields.
- `parseStoryMap` and `story-map validate` still reject unknown fields in the current map.

**Docs.** Update [Show status history](../story-map.md#show-status-history) to explain `skipped`. In `docs/ENGINEERING-OVERVIEW.md`, add a "Changing the format" rule under [Add a field to the map](../ENGINEERING-OVERVIEW.md#add-a-field-to-the-map): any change that is not purely additive must add a migration step and a history test with the old format.

## 4. Stable customer IDs and per-map collapsed lanes

Story: ESM-603. Breaking, so 0.6.0.

**Problem.** The customer view replaces internal IDs with positional ones: `activity-1`, `release-2`, `story-3`. They change whenever an earlier item becomes visible to customers or stops being visible. `board.js` remembers collapsed lanes by release ID, so after such a change a customer's collapsed lane is applied to a different release. The storage key is also just the page path, so two maps on the same path share collapsed lanes. Positional IDs also make React keys, client caches and any links to a story unstable.

**Change.**

1. **Stable, opaque IDs.** In `src/view.ts`, make customer IDs `<kind>-<hash>`, such as `release-k3f9x2m1`:
   - The hash is FNV-1a 64-bit of `<map id>\0<kind>\0<internal id>`, in base 36, cut to 10 characters. Use a small pure function, not `node:crypto`, so `view.ts` still works in browser bundles and stays synchronous.
   - The same map and internal ID always give the same customer ID, whatever else changes in the map.
   - On the rare collision within one map, append `-2`, `-3` in source order. Log nothing, because the customer view must not reveal that a collision happened.
   - See decision B: the ID hides the internal ID but is not a secret.
2. **Map identity on the board.** Add `key: string` to both view types: the hash of the map ID. The board renders it as `data-esm-map` on `.esm-board`.
3. **Per-map storage in `board.js`.** Store collapsed lanes under `esm-collapsed:<path>:<map key>`. For internal boards, read the old `esm-collapsed:<path>` value once when the new key is empty, since internal release IDs have not changed, then remove it. Ignore the old value on customer boards, because it holds positional IDs.
4. **Search.** `filterStoryMapView` already searches only titles and summaries in the customer view, so searching for the new IDs finds nothing. Keep the existing test that searching `story-1` finds nothing, and add one for the hashed form.

**Tests.**

- Making an earlier release visible to customers does not change the ID of a later one.
- Customer IDs never contain an internal ID, title or summary.
- The same input gives the same IDs across runs.
- Collision handling, through a test-only import of the ID helper from `dist/view.js` with a forced collision.
- `board.js` with two boards for different maps on one page keeps separate collapsed lanes. It migrates an old internal key and ignores an old customer key.
- The smoke test's panel checks still pass with the new IDs.

**Docs.** In `CHANGELOG.md`, mark the ID change as breaking: hosts that stored customer IDs, such as in analytics events, must map them again. Add "Upgrade to 0.6.0" to `docs/story-map.md`, and update the upgrade links in `README.md` and `AGENTS.md`, as `docs/releasing.md` requires.

## 5. An explicit rule for who sees the internal map

Story: ESM-604. Item 5a ships in 0.5.1. Item 5b is breaking and ships in 0.6.0.

**Problem.** When a host does not pass `canViewInternal`, anyone whose roles include `engineer` or `super-admin` sees the internal map: engineering notes, sources, block reasons and the names in the history. Those role names are generic. In a product for builders or engineering firms, "engineer" can easily be a customer role. The access rule fails open on a name collision the host may never notice.

**Change.**

- **5a. Warn and make the explicit rule easy (0.5.1).**
  1. Export `allowRoles(...roles)`, which returns a rule that is `true` when the viewer has any of the roles. The current behaviour becomes `canViewInternal: allowRoles("engineer", "super-admin")`.
  2. When `getStoryMapForViewer` uses the default rule, warn once per process: "Pass canViewInternal to choose who sees the internal story map. The default, the engineer and super-admin roles, is removed in 0.6.0." Use `process.emitWarning` when it exists, and `console.warn` otherwise. Skip the warning when the viewer is `null`.
  3. Update the example host, the smoke test and every snippet in `docs/story-map.md` and `README.md` to pass a rule.
- **5b. Require it (0.6.0).**
  1. Make `canViewInternal` required in `StoryMapAccessOptions`, so TypeScript hosts find every call that is missing one.
  2. At run time, a missing rule grants nobody the internal view (decision A). Viewers then get the customer view when the map allows it, or `null`. Warn once, as in 5a.
  3. Keep `defaultInternalRoles` exported, marked deprecated, for hosts that want to pass `allowRoles(...defaultInternalRoles)`.
  4. Keep the strict `=== true` check.

**Tests.**

- 5a: the default rule still grants internal access and warns once, not once per call. An explicit rule does not warn. `allowRoles` matches any listed role and nothing else.
- 5b: no rule means a viewer with the `engineer` role gets the customer view, and a map with `visibility: internal` gives that viewer `null`.
- A type test (a `.ts` file compiled with `tsc --noEmit` in `npm test`) that omitting `canViewInternal` is a compile error.

**Docs.** Update [Integrate with a product](../story-map.md#integrate-with-a-product) step 2 and the security boundaries section of `docs/ENGINEERING-OVERVIEW.md`. The 0.6.0 upgrade steps say to add `canViewInternal: allowRoles("engineer", "super-admin")` to keep today's behaviour.

## 6. One call that projects and filters

Story: ESM-605.

**Problem.** Hosts stay safe only by following the docs: call `getStoryMapForViewer` before `filterStoryMapView`, keep the internal view on the server, and send `Cache-Control: private, no-store`. Filtering before projecting would let a search reveal what a viewer may not see. The safe order should be the easy one.

**Change.**

1. Add `getStoryMapPage(document, viewer, { canViewInternal, history, stalledAfterWeeks, now, searchParams })` to `src/view.ts`, exported from the index. It projects, then reads the filters from `searchParams` and filters, and returns the view or `null`.
2. Export `storyMapResponseHeaders`, the headers the page and any JSON endpoint should send: `Cache-Control: private, no-store` and `X-Content-Type-Options: nosniff`.
3. Use both in `example/host.mjs` and the integration docs. Keep `getStoryMapForViewer` and `filterStoryMapView` for hosts that need the steps separately.
4. Document board size. The board renders a panel for every story so that panels work without JavaScript. Add a "Large maps" note with measured page sizes for 100, 500 and 1,000 stories, and suggest splitting maps or filtering by default above a few hundred stories.

**Tests.** `getStoryMapPage` gives the same result as calling the two functions in order, for internal, customer and guest viewers. A search for an internal-only word through `getStoryMapPage` finds nothing for a customer.

**Docs.** Integration steps 2 and 3, the example host, and the new "Large maps" note.

## 7. Validation and CLI fixes

Story: ESM-606.

**Problems and changes.**

1. **Duplicate impact metrics.** The diff matches impact items by `metric` through a `Map`, so two items with the same metric become one and the diff is wrong.
   - Add a warning in `storyMapWarnings`: "Impact metric '…' appears more than once in this release." Its path points at the second item (decision C).
   - In `releaseDetailChange` in `src/diff.ts`, key items by metric plus occurrence (`metric`, `metric (2)`), so duplicates are compared one to one rather than merged.
2. **Options that take the next flag.** `optionValue` in `src/cli.ts` takes the next argument even when it is another option, so `--map --strict` reads `--strict` as the map path.
   - Treat a value that starts with `-` as missing, and print `story-map: --map needs a value` before the usage text.
   - Use the same helper in `parseInitArgs`, which today parses `--dir` by hand.
3. **Symbolic links out of the repository.** `checkSources` checks the path text against the repository root, but `stat` and `readFile` follow symbolic links. A PR could add `docs/x.md` linking to any file on the CI runner, and the "has no heading" message would reveal whether that file has a given heading.
   - After the text check, compare `realpath(file)` with `realpath(root)`. Report "Source '…' points outside the repository through a symbolic link." and do not read the file.
   - Apply the same check to `--plans` paths and to the files found under them.

**Tests.**

- A release with two items for one metric warns once, and the diff reports a change to the second without touching the first.
- `story-map validate --plans --strict map.yaml` and `story-map history --map --allow-shallow` exit 2 with the option named.
- A source that is a symbolic link to a file outside a temporary repository is reported and not read. A link to a file inside the repository still works.

**Docs.** Mention the new warning in [Release notes and impact](../story-map.md#release-notes-and-impact) and the symbolic link rule in [Validate a change](../story-map.md#validate-a-change).

## 8. Diff summaries that do not notify people

Story: ESM-607.

**Problem.** `AGENTS.md` asks for the `story-map diff` summary in PR descriptions. The diff's `text()` escaping handles HTML and Markdown, but not GitHub's references. A story titled "Ask @finance-team" notifies that team when the summary is pasted, and `#123` can link an unrelated issue.

**Change.**

1. In `text()` in `src/diff.ts`, write `@` as `&#64;` and `#` as `&#35;`. `#` is currently escaped with a backslash, which stops headings but not issue links.
2. Check on a real PR that GitHub renders both entities as plain characters and links neither. If it does link them, use `@<!-- -->` instead, which GitHub's own docs suggest.
3. Story IDs in backticks are already safe, because the map limits IDs to letters, numbers, `-` and `_`.

**Tests.** A story, release and activity title containing `@someone`, `@org/team` and `#12` produces a summary with none of those strings, and the summary still reads correctly as text.

**Docs.** None beyond the changelog.

## 9. A board that survives bad date settings

Story: ESM-608.

**Problems.**

- An unknown `timeZone` or `locale` passed to `StoryMapBoard` makes `Intl.DateTimeFormat` throw `RangeError`, so the whole page fails.
- `formatDate` builds a new `Intl.DateTimeFormat` for every date. A map with history formats several dates per story.
- `cells.set(key, [...existing, story])` copies a cell's list for every story it adds.

**Change.**

1. Add a `dateFormatters(locale, timeZone)` helper in `src/react.tsx` that builds the formatters once per render:
   - It tries the host's locale and time zone, falls back to `en-GB` for a bad locale and to the runtime's zone for a bad time zone, and warns once on the server.
   - `formatDate` and `formatRelative` use it.
2. Build `cells` with `push` on an existing array.

**Tests.** Rendering with `timeZone="Nowhere/Nope"` or `locale="not a locale"` succeeds and shows dates. Rendered markup for the fixture maps is unchanged by the refactor (compare with the output from before the change).

**Docs.** Note the fallback in the board props table.
