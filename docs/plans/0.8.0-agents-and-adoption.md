# Plan: agents and adoption

Status: shipped. The work is ESM-116, ESM-117 and ESM-118 in the **0.7.6: Triage, readiness and agent access** release of the map, and ESM-119 in **0.7.7: Delivery plans and test tags**. The three moved from 0.7.7 to 0.7.6 to reach agents and new adopters sooner. The estimates below are agreed.

Most people adopt a story map months into a project, and more and more of them work through a coding agent that expects an MCP server or a skill rather than a section of `AGENTS.md`. This release makes the map easier for agents to reach, and easier to start on a repository that already has history.

Items are numbered in the order they should be built:

1. [Serve the CLI over MCP](#1-serve-the-cli-over-mcp) (ESM-116)
2. [Install a story map skill](#2-install-a-story-map-skill) (ESM-117)
3. [Survey a repository for its first map](#3-survey-a-repository-for-its-first-map) (ESM-118)
4. [Tag a describe block for all its tests](#4-tag-a-describe-block-for-all-its-tests) (ESM-119)

The release comes after 0.7.5. The MCP server wraps the evidence and claim commands from 0.7.5, and the survey reuses their Git and tag reading. The plan comes from a review of outside suggestions. What was left out, and why, is in [Not now](#not-now).

## 1. Serve the CLI over MCP

`story-map mcp` runs a Model Context Protocol server over standard input and output, for agents that call tools rather than run commands. It is a thin layer over the library functions behind the CLI, so it adds no new behaviour:

| Tool | Wraps |
| --- | --- |
| `list_stories`, `get_story`, `list_releases` | `story-map stories`, `story` and `releases` |
| `validate_map` | `story-map validate --format json` |
| `get_evidence` | `story-map evidence` (ESM-105) |
| `propose_edit` | `story-map edit --from`, as a dry run unless the call sets `write` |
| `claim_story` | `story-map claim` (ESM-106) |

- **Same safeguards as the CLI.** `propose_edit` refuses what `edit` refuses: deletes, removing `draft`, and customer copy without `customer`. Paths stay inside the repository root. There is no tool for `story-map confirm` (ESM-110), because only a person confirms drafts.
- **Local only.** Standard input and output, with no network listener.
- **Dependency, decided:** the official MCP SDK, as an optional peer dependency that only `story-map mcp` loads, like React for `preview`. A regular runtime dependency would add the SDK's own dependencies, such as Express and Hono, to every host's install, and a small JSON-RPC handler would mean tracking protocol changes ourselves. Without the SDK, `story-map mcp` says how to install it.
- **No persona edits.** `propose_edit` leaves out the persona and job operations that `edit --from` takes for the preview, so an agent cannot delete a job or add one that is not a draft.

Estimate: 5 points.

## 2. Install a story map skill

`story-map init --skill` writes a `SKILL.md` that holds the story map rules from `AGENTS.md` and the commands agents use most. A skill loads only its description until the task needs it, while `AGENTS.md`, about 730 words for the story map section, is read in every session.

- The skill and the `AGENTS.md` section come from the same template, so they cannot drift apart. A test checks that both carry every rule.
- The skill goes in `.claude/skills/story-map/SKILL.md`, where Claude Code loads skills.
- `AGENTS.md` keeps a short pointer to the skill, for agents that do not read skills. It also keeps the rules that cost most when missed: never remove `draft`, put the story ID in branches, commits, titles and test names, and validate after each map change.
- Existing files are never overwritten, as with the rest of `init`.
- ESM-152 adds the planning rules to the same template. See [Carry the planning rules in the skill](host-planning-guidance.md#6-carry-the-planning-rules-in-the-skill).

Estimate: 2 points.

## 3. Survey a repository for its first map

`story-map survey --format json` collects the facts an agent needs to draft a first map for a repository that already has history, as one document:

- **Releases:** release tags and `CHANGELOG.md` versions, with dates, as suggested releases.
- **Sources:** Markdown docs and their headings, as candidate `sources` and engineering overviews.
- **Planned work:** open plan docs, and `TODO` and `FIXME` comments, with file and line.

It reads and suggests only. Turning months of commits into stories takes judgement, so the agent still drafts the stories, following the [first-run workflow](../story-map.md#populate-the-first-map), which gains a step to run the survey first and cite it. The evidence command (ESM-105) cannot do this on its own, because it finds work by story ID, and a repository adopting the map has none yet.

Git and tags are read with `execFile` and argument arrays, as in ESM-105, and output is capped in size like the tests index.

Estimate: 5 points.

## 4. Tag a describe block for all its tests

A story ID in the name of a `describe` or `suite` block now covers every test inside it, so a test renamed during a refactor stays linked to its story. Today a tagged block is listed once, as a group, and the tests inside it are not linked unless they are tagged too. This answers the first open question in [the story tests plan](story-tests.md#open-questions).

- The scanner in `src/tests.ts` already reads `describe` calls. It now tracks nesting, so each test inherits the IDs of the blocks around it.
- The panel lists those tests under the story, each marked as covered by its block.
- Free-standing comment tags, such as `// @story ESM-101`, stay out, because a comment can sit far from the tests it means.

Estimate: 3 points.

## Not now

- **Pass and fail results from CI.** Planned in [Later: results](story-tests.md#later-results). Boards are usually built from the default branch, where CI has already required the tests to pass, so cards would nearly always show green. It becomes worth building when hosts show boards for branch previews.
- **A `lean` validation mode.** See [Not planned](local-triage.md#not-planned).
