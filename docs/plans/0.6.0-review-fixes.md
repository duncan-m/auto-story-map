## 1. Publish without running dependency scripts

**Problem.** The `publish` job in `.github/workflows/release.yml` has `id-token: write` and runs `npm ci` with install scripts turned on. Every step in the job can ask GitHub for an OpenID Connect token. A compromised dependency's install script could use that token to publish a malicious version through trusted publishing, and the version would get a valid provenance statement. The `contents: write` token is only given to the last step, so that part is already fine.

The first npm release is published by hand, as [Set up publishing once](../releasing.md#set-up-publishing-once) describes, so this protects every release after it. It should still be in place before trusted publishing is turned on.

**Change.**

1. Build and pack once, in a job that has no publishing permissions:
   - Add a `pack` job after `check`, with `permissions: contents: read`. It runs `npm ci --ignore-scripts`, `npm run build` and `npm pack`, and uploads the `.tgz` with `actions/upload-artifact`, pinned to a commit SHA like the other actions.
2. Make `publish` install nothing:
   - Download the artifact, then run `npm publish ./embedded-story-map-<version>.tgz --provenance --access public`. Publishing a tarball does not run `prepare` or any dependency scripts.
   - Keep the tag and changelog checks. They only need `node -p` and `grep`.
   - Drop `cache: npm` from `publish`, since it no longer installs anything.
3. Check that the tarball's `package.json` version matches the tag before publishing.
4. In `check`, use `npm ci --ignore-scripts` followed by an explicit `npm run build`.

**Tests.** Run the workflow against a test tag with `npm publish --dry-run`, and check that the publish job logs show no `npm ci` and that the file list matches `npm pack --dry-run`.

**Docs.** Update `docs/releasing.md` to describe the pack and publish split, and to say why the publish job must never install dependencies. For the first manual publish, publish from a clean `npm ci --ignore-scripts && npm run build`.

## 2. History names that fit the history format

Story: ESM-601.

**Problem.** `storyMapHistorySchema` limits `by` and `mergedBy` to 120 characters, but Git author and committer names have no limit. A 130-character author name produced a history file that `parseStoryMapHistory` rejects, so the host's build or page fails. This happened because the writer (`src/history-git.ts`) and the reader (`src/history.ts`) each describe the format separately.

**Change.**

1. Export one constant, `historyNameMaxLength = 120`, from `src/history.ts` and use it in the schema.
2. In `buildStoryMapHistory`, pass every name through a `historyName(name)` helper: trim it, drop it if empty, and truncate by Unicode code points (so emoji are never split), ending with `…` within the limit.
3. Apply it to `by`, `mergedBy` and `lastEdits[].by`. Also limit `reason` to 500 characters in the writer.
4. Keep the documented interfaces in `src/history.ts`, and add a compile-time check that `z.infer<typeof storyMapHistorySchema>` and `StoryMapHistory` are the same type, so `tsc` fails if either changes without the other.

**Tests.**

- A commit by a 130-character author produces a history that `parseStoryMapHistory` accepts, with `by` at 120 code points ending in `…`.
- A name made of emoji is truncated without a lone surrogate.
- Every history the existing Git tests build passes `parseStoryMapHistory`. Add this to the shared test helper.

## 3. History and diff that survive format changes

Story: ESM-602.

**Problem.** `buildStoryMapHistory` parses every past version of the map with today's strict schema and silently skips any version that fails. So far every format change has only added fields. The first time a change removes or renames a field, or removes a status, every older version stops validating: their events disappear, every story looks newly added at the first version that does validate, in-progress dates and the stalled flag become wrong, and nothing says so. In the same situation, `story-map diff` stops with an error because the base branch's map is not valid, so CI fails until the change merges.

**Change.**

1. **A lenient parser for past versions.** Add `loadHistoricalStoryMap(source)` in `src/schema.ts`, not exported from the package index.
   - Same YAML safety settings as `loadStoryMap`: unique keys and `maxAliasCount: 20`.
   - Builds the schema from the same field definitions with a `strict` switch, so there is still one description of the format. In lenient mode, unknown keys are dropped instead of failing.
   - Parses each story on its own. A story that still fails, such as one with a status that no longer exists, is dropped and counted rather than failing the whole version.
   - Skips the cross-reference checks.
   - Returns `{ map, dropped: { stories, fields } }`.
2. **A migration step.** Add `migrateStoryMap(data)`, run before validation in both parsers. It does nothing today. It is where a rename or status mapping goes the next time the format changes.
3. **History uses it and says what it skipped.** `buildStoryMapHistory` only skips a version when the YAML cannot be read or the file is missing. Add optional `skipped` (`{ commit, reason }`, at most 100) and `skippedCount` fields to the history format. The CLI prints a warning naming the first few commits and still exits 0.
4. **Diff uses it for the base version only.** `readMapAt` in `src/cli.ts` reads the base leniently. The current map is still checked strictly. When anything was dropped, the summary starts with a note that the base uses an older format, and the exit code stays 0.

**Tests.**

- Early commits with an unknown field keep their `added` events and original dates.
- A version with an unknown status drops only that story.
- A version that is not valid YAML is listed in `skipped`, and the CLI warning names it.
- `story-map diff` against a base with an unknown field prints the note and exits 0.
- `parseStoryMapHistory` accepts files with and without the new fields.
- `story-map validate` still rejects unknown fields in the current map.

**Docs.** Explain `skipped` in [Show status history](../story-map.md#show-status-history). Under [Add a field to the map](../ENGINEERING-OVERVIEW.md#add-a-field-to-the-map), add the rule that any change that is not purely additive needs a migration step and a history test with the old format.

Story: ESM-604. Cut.

**Decision.** Out of scope for this release. The default stays: viewers with the `engineer` or `super-admin` role see the internal map unless the host passes `canViewInternal`. The risk is recorded in the [engineering overview](../ENGINEERING-OVERVIEW.md#audience-projection).

## 6. One call that projects and filters

Story: ESM-605.

**Problem.** Hosts stay safe only by following the docs: call `getStoryMapForViewer` before `filterStoryMapView`, keep the internal view on the server, and send `Cache-Control: private, no-store`. Filtering before projecting would let a search reveal what a viewer may not see. The safe order should be the easy one.

**Change.**

1. Add `getStoryMapPage(document, viewer, { canViewInternal, history, stalledAfterWeeks, now, searchParams })` to `src/view.ts`, exported from the index. It projects, then reads the filters from `searchParams` and filters, and returns the view or `null`.
2. Export `storyMapResponseHeaders`: `Cache-Control: private, no-store` and `X-Content-Type-Options: nosniff`.
3. Use both in `example/host.mjs` and the integration docs. Keep `getStoryMapForViewer` and `filterStoryMapView` for hosts that need the steps separately.
4. Add a "Large maps" note with measured page sizes for 100, 500 and 1,000 stories, and suggest splitting maps or filtering by default above a few hundred stories.

**Tests.** `getStoryMapPage` gives the same result as calling the two functions in order, for internal, customer and guest viewers. A search for an internal-only word through `getStoryMapPage` finds nothing for a customer.

## 7. CLI and source check fixes

Story: ESM-606.

1. **Options that take the next flag.** `optionValue` in `src/cli.ts` takes the next argument even when it is another option, so `--map --strict` reads `--strict` as the map path. Treat a value that starts with `-` as missing, print `story-map: --map needs a value` before the usage text, and use the same helper for `--dir` in `parseInitArgs`.
2. **Symbolic links out of the repository.** `checkSources` checks the path text against the repository root, but `stat` and `readFile` follow symbolic links, so a PR could link `docs/x.md` to any file on the CI runner and learn from the error whether it has a given heading. After the text check, compare `realpath(file)` with `realpath(root)`, report "points outside the repository through a symbolic link" and do not read the file. Apply the same check to `--plans` paths and the files found under them.

**Tests.**

- `story-map validate --plans --strict map.yaml` and `story-map history --map --allow-shallow` exit 2 with the option named.
- A source that is a symbolic link to a file outside a temporary repository is reported and not read. A link inside the repository still works.

**Docs.** Mention the symbolic link rule in [Validate a change](../story-map.md#validate-a-change).

## 8. Diff summaries that do not notify people

Story: ESM-607.

**Problem.** `AGENTS.md` asks for the `story-map diff` summary in PR descriptions. The diff escapes HTML and Markdown, but not GitHub references. A story titled "Ask @finance-team" notifies that team when the summary is pasted, and `#123` can link an unrelated issue.

**Change.** In `text()` in `src/diff.ts`, write `@` as `&#64;` and `#` as `&#35;`. Check on a real PR that GitHub links neither. If it does, use `@<!-- -->` instead.

**Tests.** Titles containing `@someone`, `@org/team` and `#12` produce a summary with none of those strings, and the summary still reads correctly.

## 9. A board that survives bad date settings

Story: ESM-608.

**Problems.** An unknown `timeZone` or `locale` passed to `StoryMapBoard` makes `Intl.DateTimeFormat` throw, so the whole page fails. `formatDate` also builds a new formatter for every date, and `cells.set(key, [...existing, story])` copies a cell's list for every story it adds.

**Change.** Add a `dateFormatters(locale, timeZone)` helper in `src/react.tsx` that builds the formatters once per render, falls back to `en-GB` for a bad locale and to the runtime's zone for a bad time zone, and warns once. Build `cells` with `push`.

**Tests.** Rendering with `timeZone="Nowhere/Nope"` or `locale="not a locale"` succeeds and shows dates. Rendered markup for the fixture maps is otherwise unchanged.

## Not now

- **Requiring an explicit access rule.** Revisit if the library is used in products where customers can have internal-sounding roles (decision A).
- **Stable customer IDs.** If collapsed lanes moving between releases becomes a problem, give customer items stable stand-in IDs rather than positions (decision B).
- **Duplicate impact metrics** (decision C).
- **Collapsed lanes per map.** `board.js` stores collapsed lanes per page path, so two different maps on the same path share them. Rare enough to leave.
- **Panels that load on demand.** Rendering only the open panel would need client JavaScript, which goes against the board's no-JavaScript design. Item 6 documents the size limits instead.
