# Plan: story map enhancements for 0.4.0

Status: in progress. Items 1 and 3 are built and unreleased. The rest is proposed, for engineering review.

This plan covers six enhancements agreed with product, plus the validator groundwork they share. Items are numbered in the suggested order, and each section uses the same number:

1. [Validator warnings](#1-groundwork-validator-warnings) (groundwork) · built
2. [Release notes and expected impact](#2-release-notes-and-expected-impact), with [editing on the board](#editing-on-the-board) as 2b
3. [Blocked and cut statuses, hidden by default](#3-blocked-and-cut-statuses) · built
4. [Flag stories that stay in progress too long](#4-flag-stories-that-stay-in-progress-too-long)
5. [“Last updated” from Git](#5-last-updated-from-git)
6. [Expandable steps within activities](#6-expandable-steps-within-activities)
7. [A scheduled agent that audits the map against the code](#7-scheduled-map-audit)

All of them are for internal viewers (engineers and product). The customer view does not change, except that blocked and cut stories never appear in it.

The board stays read-only, except for editing a release’s notes and expected impact (see [Editing on the board](#editing-on-the-board)). Every change to the map, including those edits, still goes through a PR.

## Decisions already made

| Topic | Decision |
| --- | --- |
| Blocked and cut | Separate statuses. Hidden by default, shown on request, so the team can review what was not done or was cut. |
| Steps | Optional. Activities are collapsed by default and expand to show their steps. |
| One map file | Keep a single `product/story-map.yaml` for now. |
| Keeping the map accurate | A scheduled agent checks the code and proposes corrections in a PR. |
| In progress | A story is in progress when an open PR or a branch refers to it. |
| Shipped | A story is shipped when its work is merged to the default branch (`main` or `master`). This replaces “available to its intended users” in the guide. |
| Release impact | Recommended but optional. CI warns but does not fail without it. An agent can draft it and a person adjusts it. |
| Editing on the board | Release notes and expected impact can be edited on the board. Everything else stays read-only. |
| Release notes length | Up to 800 characters. |
| Long-running work | A story in progress for longer than a configurable number of weeks (default 4) is flagged. |
| “Last updated” | Worked out from Git. `updatedBy` becomes optional. |

## 1. Groundwork: validator warnings

Today every validation problem is an error that fails CI. Release impact needs a softer level.

- Add `severity: "error" | "warning"` to `StoryMapIssue`.
- Errors throw `StoryMapValidationError` as now. Warnings come back alongside a successful parse: `loadStoryMap` returns `{ map, locate, warnings }`.
- CLI: print warnings, exit 0 if there are only warnings. `--format github` emits `::warning` annotations. Add `--strict` to treat warnings as errors for teams that want it.

**Tests:** a map with only warnings exits 0 and prints them; `--strict` exits 1; GitHub format uses `::warning`.

## 2. Release notes and expected impact

### YAML

```yaml
releases:
  - id: builder-mvp
    title: Builder workflow
    summary: Deliver the builder interface and the backend it needs.
    notes: |
      Builders can price and submit estimates without emailing finance.
      Catalogue prices are locked when the estimate is submitted.
    impact:
      - metric: Estimate turnaround time
        expected: Decrease from 3 days to 1 day
        solves: Builders waiting on finance for prices
      - metric: Estimates returned for corrections
        expected: Decrease by 50%
        solves: Wrong unit prices typed by hand
        draft: true
```

| Field | Rules |
| --- | --- |
| `notes` | Optional. Plain text up to 800 characters. Blank lines separate paragraphs. No Markdown in the first version. |
| `impact` | Optional list, up to 10 items. |
| `impact[].metric` | Required. What is measured. |
| `impact[].expected` | Required. The expected change, written for people, such as “Increase by 10%”. Not parsed. |
| `impact[].solves` | Optional. The problem it addresses. |
| `impact[].actual` | Optional. The measured result, added after shipping. |
| `impact[].draft` | Optional. `true` when an agent drafted it and nobody has confirmed it yet. |

`expected` stays free text on purpose. Structured numbers (baseline, target, unit) can come later if teams want charts.

### Validation

- **Warning:** a release with stories but no `impact`.
- **Warning:** an `impact` item still marked `draft: true` in a release with shipped stories.
- No errors, so CI never fails because of impact.

### Board

- **Lane heading:** below the release title, show the first impact item in one line, such as “Estimate turnaround time: decrease from 3 days to 1 day”. Show “+1 more” when there are more. Drafts show a small “Draft” label.
- **Release panel:** the release title becomes a button that opens a panel (the same popover pattern as story cards). It shows:
  - the summary and notes,
  - every impact item, with its expected and actual result, and what it solves,
  - progress, such as “3 of 5 stories shipped, 1 cut”,
  - the release’s stories, grouped by status, each opening its own story panel.
- Internal only. The customer view keeps its existing `customer.title` and `customer.summary` for releases.

### Editing on the board

People who are allowed to edit can change a release’s notes and impact items from the release panel. Saving proposes the change as a PR, so the map file stays the single source of truth and the change is reviewed like any other.

**Who can edit:** a new `canEditReleases` rule on `getStoryMapForViewer`, decided by the host like `canViewInternal`. It defaults to nobody, so hosts opt in. The view tells the board whether to show the **Edit** button.

**The form:**

- An **Edit** button in the release panel opens a form with the notes (limited to 800 characters, with a counter) and one row per impact item: metric, expected, solves and actual. There is an empty row for adding an item, and each row can be removed.
- Saving an impact item clears its `draft` flag, because a person has now confirmed it.
- The form is a plain `<form method="post">` to a URL the host provides (`releaseEditAction`). It works without JavaScript, like the filters. The host passes any CSRF token or other hidden fields with `formFields`.

**Saving, in the library:**

- `updateRelease(source, releaseId, { notes, impact })` edits the YAML text and returns the new text. It keeps comments, ordering and formatting elsewhere in the file, and validates the result before returning it.
- A new server-only entry point, `embedded-story-map/github`, provides `proposeStoryMapChange({ token, repository, baseBranch, path, content, title, body, coAuthor })`. It creates a branch, commits the new file and opens a PR through the GitHub API. The commit carries a `Co-authored-by` trailer for the person who made the edit, so Git credits them (see item 5).

**Saving, in the host:** the host’s POST handler checks the signed-in viewer against `canEditReleases`, checks the CSRF token, calls `updateRelease`, then `proposeStoryMapChange`. It redirects back to the board with a message: “Your changes to Builder workflow are in PR #N. They appear on the board once it is merged and deployed.” The example host will show this end to end.

**Safeguards:**

- Permission is checked on the server for every save. Hiding the button is not the protection.
- Only `notes` and `impact` on the named release can change. The release ID must exist, and every other field and release is left untouched. Tests compare the rest of the file byte for byte.
- Text is limited to the schema’s lengths and validated before anything is committed.
- The GitHub token needs only `contents: write` and `pull-requests: write` on the one repository, and stays on the server.

**Not in this round:** showing pending edits on the board (for example “Edit in review · PR #N”), and editing anything other than release notes and impact.

### Diff and agents

- `story-map diff` lists added or changed impact items, and calls out an `actual` being recorded.
- The first-run workflow and the audit agent (item 7) may draft impact items with `draft: true`. Only a person removes `draft`. The agent instructions say so.

**Tests:** schema accepts and rejects the fields above, including notes longer than 800 characters; warnings fire as described; lane heading and panel render; customer HTML and JSON contain no notes or impact; diff output.

**Tests for editing (2b):** `updateRelease` changes only the named release’s notes and impact, keeps comments and formatting, rejects unknown releases and invalid text, and clears `draft` on saved items; the form renders only when `canEditReleases` allows it, and never for customers; `proposeStoryMapChange` against a mocked GitHub API (branch, commit with the co-author trailer, PR); the example host refuses saves from viewers without permission or with a bad CSRF token.

## 3. Blocked and cut statuses

### Statuses

`planned`, `in-progress`, `shipped`, plus:

- `blocked`: started or agreed, but cannot continue.
- `cut`: deliberately dropped from its release.

Add an optional `statusReason` field (up to 500 characters) so the map records why. The validator warns when a blocked or cut story has no `statusReason`.

```yaml
- id: FINANCE-202
  title: Explore duplicate approval handling
  status: cut
  statusReason: Finance will handle duplicates manually until volumes justify it.
```

### Hidden by default

- The board shows **Active** stories by default: planned, in progress and shipped.
- The status filter becomes:
  - **Active** (default)
  - **All, including blocked and cut**
  - Planned, In progress, Shipped, Blocked, Cut (each on its own)
- When stories are hidden, the toolbar says so, such as “2 blocked and 1 cut hidden · Show”, so nobody mistakes the default view for the whole map.
- Release lane counts follow the filter.
- `filterStoryMapView` applies the Active default when no status is given. Hosts can pass `status: "all"`.

### Elsewhere

- **Customer view:** blocked and cut stories never appear. A customer-visible story that becomes blocked or cut shows under “No longer visible” in the diff.
- **Diff:** a separate “Blocked and cut” section, listing stories that entered or left these statuses, with their reasons. As built, it comes straight after “Customer-facing changes”, which stays first.
- **History:** works unchanged. Entries show the reason when there is one.
- **Icons:** blocked uses a circle with a bar; cut uses a struck-through circle. Both need a dark-theme colour and a text label, never colour alone.

**Tests:** default filtering hides both statuses; each filter option; hidden-count message; customer projection excludes both; diff section; schema and warnings for `statusReason`.

## 4. Flag stories that stay in progress too long

### Rule

A story is **stalled** when it has been `in-progress` for longer than the threshold. The time is measured from the history entry where it last became in progress, so it needs the history file from `story-map history`.

Stalled is a flag, not a status. Nothing changes the YAML automatically. The audit agent (item 7) can propose moving a stalled story to `blocked` with a reason, for a person to approve.

### Setting the threshold

The board is read-only and has no settings screen, so the threshold lives in two places:

```yaml
# product/story-map.yaml
settings:
  stalledAfterWeeks: 4   # default 4; 0 turns the flag off
```

- The map setting is the default for everyone, changed through a PR.
- Hosts can override it with a `stalledAfterWeeks` option on `getStoryMapForViewer`, for example from their own admin settings.

### Board

- A stalled card shows a warning label, such as “In progress for 6 weeks”, in place of the usual “3 days ago”.
- The story panel says when it became in progress and that it is stalled.
- A **Stalled** option in the status filter.
- Without a history file there is no flag, because the start date is unknown.

**Tests:** threshold from the map, host override, 0 turns it off; a story that went in progress, back to planned and in progress again is measured from the latest start; filter; no flag without history.

## 5. “Last updated” from Git

- Extend `story-map history` to record each story’s last edit to any field, not only status changes: `lastEdit: { at, by, commit }`. Moves count as edits here, because this is about “who last touched it”, not the Changed filter.
- **Who:** the commit author of the edit, or `updatedBy` if that edit set it. For bot authors (names ending in `[bot]`, or a list set with `--bot-names`), credit the person who merged instead.
- The panel shows “Last updated 3 days ago by Sam Patel” from `lastEdit`. Without a history file it falls back to `updatedBy` as today.
- `updatedBy` becomes optional guidance. The agent instructions stop requiring it and say to set it only when the commit author is not the person to credit.

**Tests:** edits to notes, sources and placement update `lastEdit`; bot commits credit the merger; fallback to `updatedBy` without history.

## 6. Expandable steps within activities

### YAML

```yaml
activities:
  - id: prepare
    title: Prepare estimate
    steps:
      - { id: choose-project, title: Choose project }
      - { id: add-materials, title: Add materials }
      - { id: review-total, title: Review total }

stories:
  - id: BUILDER-102
    title: Look up prices in the material catalogue
    activity: prepare
    step: add-materials
    release: builder-mvp
```

- `steps` is optional on each activity. `step` is optional on each story.
- **Validation errors:** unknown step, or a step that belongs to a different activity. Step IDs are unique within their activity.
- Maps without steps behave exactly as today.

### Board

- Activities are collapsed by default: one column each, as today. A tile with steps shows “3 steps” and an expand control.
- Expanding an activity splits its column into one column per step. Stories without a step go in a “No step” column.
- Expansion is a link that sets `?expand=prepare` (comma-separated, or `expand=all`), handled on the server like the filters. It works without JavaScript, survives filtering and can be shared.
- **Expand all** and **Collapse all** in the toolbar when any activity has steps.
- Phones: steps become sub-headings inside each activity, with no expand control needed.
- `readStoryMapFilters` gains `expand`. The board receives the expanded set and builds the grid columns from it.

### Elsewhere

- **Diff:** a step change is a move. It is listed under stories, and does not count as a change for the Changed filter or the history.
- **Customer view:** steps need their own `customer.title` before they show to customers. Until then, customers see collapsed activities only.

**Tests:** schema and validation; grid columns for collapsed, partly expanded and all expanded; “No step” column; URL handling with filters; mobile markup; diff.

## 7. Scheduled map audit

### Purpose

The map can drift from reality when a PR forgets to update it. A scheduled agent checks the code and Git activity, then opens a PR with corrections for a person to review. It never commits to the default branch directly.

### Linking work to stories

The audit relies on story IDs appearing in the work:

- branch names, such as `BUILDER-102-catalogue-prices`,
- PR titles or bodies,
- commit messages.

The agent instructions and the guide will ask for this. Work without an ID can still be matched by the agent reading the code, but with lower confidence, and the PR says so.

### Part 1: evidence command (deterministic)

`story-map audit --format json` gathers facts without changing anything:

| Signal | Source | Suggests |
| --- | --- | --- |
| A branch whose name contains the story ID | `git for-each-ref` | in progress |
| An open PR that mentions the story ID | GitHub API, when a token is available | in progress |
| A commit on the default branch that mentions the story ID | `git log` on `main` or `master` | shipped |
| In progress past the stalled threshold | history | stalled |
| A source file or heading that no longer exists | existing `--check-sources` | outdated sources |
| A release with stories but no impact | validator warning | needs impact |

For each story it reports the current status, the suggested status, and the evidence (branch, PR or commit). It never suggests moving a shipped story backwards, or changing a `cut` story.

### Part 2: the agent

A scheduled GitHub Actions workflow, weekly by default with the schedule in the workflow file:

1. Check out the full history and run `story-map audit`.
2. Give the agent the evidence and the guide. The agent:
   - applies the status suggestions it can confirm,
   - reads the code to check that shipped stories really exist, and that the map covers features it finds in the code,
   - proposes moving long-stalled stories to `blocked` with a `statusReason`,
   - drafts missing release impact with `draft: true`,
   - fixes broken sources.
3. Validate the map, then open or update a single PR titled “Story map audit”. The PR body has the `story-map diff` summary, the evidence for each change, and a list of anything it could not confirm.
4. If nothing needs changing, it opens no PR.

The agent can be any coding agent that runs in GitHub Actions. We will ship the workflow as a template from `story-map init --audit`, using the Claude Code GitHub Action by default, with the prompt kept in `.github/story-map-audit.md` so teams can edit it.

### Safeguards

- PR only, never a direct push. The workflow needs `contents: write` and `pull-requests: write`, and nothing else.
- One open audit PR at a time. A new run updates it instead of opening another.
- Customer-facing copy is never added or changed by the audit.
- `updatedBy` is not set by the agent. “Last updated” credit comes from Git (item 5), with the bot rule crediting whoever merges.

**Tests:** the evidence command against a scratch repository with branches, merged work and stalled stories; the “never backwards” rules; workflow template validity. The agent step itself is reviewed by running it on this repository and one real host before release.

## Questions for review

1. **Shipped means merged.** Teams that deploy separately from merging will show stories as shipped before users have them. Is that acceptable, or do we want an optional `deployed` signal later?
2. **Stalled from history only.** Stalled needs the history file. Is it acceptable that hosts without it get no flag, or should we fall back to the date of the last commit that touched the story?
3. **Audit agent.** Is the Claude Code GitHub Action the right default, or should the template be agent-neutral with Claude as one example?
4. **Audit schedule.** Weekly by default. Any reason to run it more often?
5. **Steps for customers.** Is it worth supporting customer-facing step titles in this round, or keep steps internal only?
6. **Saving release edits.** The plan opens a PR for each save, which means an edit appears only after the PR is merged and the product is deployed. Is that delay acceptable, or should hosts be able to commit straight to the default branch for these edits?
