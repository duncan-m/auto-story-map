# Changelog

All notable changes to `auto-story-map` are recorded here. The project follows [semantic versioning](https://semver.org). Before 1.0.0, a minor version can include breaking changes, and each one is listed with its upgrade steps.

## 0.7.5

Adds story evidence, claims for several agents, token counts, agent briefs and story dependencies. Nothing needs an upgrade step: existing maps, history files and host code keep working, and everything new is optional. Hosts turn on agent briefs in internal story and release panels with the new `brief` option of `getStoryMapForViewer` or `getStoryMapPage`, and the **Open in** links with the new `webAgents` board prop. Hosts that copied the `AGENTS.md` template can copy its new paragraphs on claims and tokens from `node_modules/auto-story-map/templates/AGENTS.md`.

### Evidence for a story

- New `story-map evidence [<ID> ...]` reports, for each story or every active story, the branches whose names contain its ID, the commits on the default branch that mention it, the Markdown lines that mention it, its tagged tests, its broken sources and, with `--history`, whether it is stalled. It suggests a status with its reasons and changes nothing. A commit suggests `merged` only when its title names the story and it changes more than Markdown, the map and files under `--plans`. It never suggests moving a story back from merged or shipped, never changes a cut story and never suggests shipped. Takes `--format json`, `--default-branch`, `--plans`, `--tests`, `--history`, `--map` and `--root`. See [Look up the evidence for a story](https://github.com/duncan-m/auto-story-map/blob/main/docs/story-map.md#look-up-the-evidence-for-a-story).
- `story-map evidence --shipped-tags <pattern>`, such as `--shipped-tags 'v*'`, suggests `shipped` for a merged story whose merging commit is in a Git tag that matches the pattern, and names the earliest such tag as `shippedIn`, so stories stop waiting in merged after a release goes out. Opt-in: without it, evidence never suggests shipped. The pattern goes to `git tag --list` as an argument, never through a shell. New option `shippedTags` for `gatherStoryEvidence` and type `EvidenceTag`. See [Suggest shipped from release tags](https://github.com/duncan-m/auto-story-map/blob/main/docs/story-map.md#suggest-shipped-from-release-tags).
- New export `gatherStoryEvidence(source, options)`, which takes the map's source text and throws `StoryMapValidationError` for an invalid map, with `StoryEvidenceError`, `evidenceItemsMaxItems`, `evidenceTextMaxLength` and types `StoryEvidence`, `StoryEvidenceOptions`, `StoryEvidenceResult`, `EvidenceBranch`, `EvidenceCommit`, `EvidenceMention` and `EvidenceTest`.

### Claims for several agents

- New `story-map claim <ID> --agent <name>` records that an agent is on a story, before any branch or pull request exists, so a second agent is told before it starts the same work. Each claim is a Git ref, `refs/story-map/claims/<ID>`, on `origin` or `--remote <name>`, pointing at a parentless commit whose message is the claim as JSON. The push only succeeds when the ref does not exist, so of two agents claiming at once exactly one wins, and the other exits 3 and is told who holds the claim, on which branch and until when. Claims last 4 hours, or `--ttl`, such as `30m` or `2d`, up to 30 days. `--renew` extends your own claim and `--take-over` replaces an expired one, both leasing against the claim that was read. Stories that are not in the map, or are merged, shipped or cut, cannot be claimed. The map is never changed. See [Coordinate several agents](https://github.com/duncan-m/auto-story-map/blob/main/docs/story-map.md#coordinate-several-agents).
- New `story-map claims` lists claims, marking expired ones, and `story-map unclaim <ID>` releases one, refusing another agent's claim when `--agent` is given. All three take `--format json`.
- `--store <dir>` keeps claims as files in a folder inside the repository instead, using exclusive file creation for the same guarantee, for agents on one machine that cannot push refs.
- `story-map evidence --claims` adds each story's claim to its evidence and reports a claim on a merged, shipped or cut story as stale. `--claims-remote` and `--claims-store` read them from elsewhere. New option `claims` for `gatherStoryEvidence`, type `EvidenceClaim`, and `claims` in `checked`.
- Claims hold an agent name, never a person: the commit is credited to `story-map`, and an agent name that looks like an email address is refused.
- New exports `claimStory`, `listStoryClaims`, `releaseStoryClaim`, `parseClaimTtl`, `describeClaim`, `claimTime`, `StoryClaimError`, `StoryClaimHeldError`, `claimRefPrefix`, `defaultClaimTtlMs`, `claimTtlMaxMs`, `claimAgentMaxLength` and `claimBranchMaxLength`, and types `StoryClaim`, `StoryClaimOptions`, `StoryClaimSource`, `ClaimStoryOptions` and `ClaimStoryResult`.
- The agent instructions from `story-map init` ask agents to claim a story before they start it when their team uses claims.

### Tokens used to deliver a story

- Stories can record the model tokens used to deliver them in a new optional `tokens`, a whole number, set in the pull request that finishes the story. The internal story panel lists it as **Tokens used**, `story-map story` prints it, the JSON export carries it, and `story-map diff` shows a change as “Tokens used: none → 4,348,638”. Customers never see it. See [Record the tokens used on a story](https://github.com/duncan-m/auto-story-map/blob/main/docs/story-map.md#record-the-tokens-used-on-a-story).
- New `story-map tokens <ID>` counts the tokens Claude Code used on a story from its session logs on this machine: every response on a branch whose name contains the story ID, or on a `--branch` or in a `--session` given, each response once, subagents included. It prints input, output, cache-write and cache-read tokens and their total, and the edit that records it. `--format markdown` prints a **Tokens used** section for the pull request, and `--format json` the counts. It changes nothing, makes no network calls and exits 1 when it finds nothing. `--logs` reads another folder than `$CLAUDE_CONFIG_DIR/projects` or `~/.claude/projects`.
- Stories can also record `estimatedCostUsd`, the estimated cost of those tokens in US dollars, shown as **Estimated cost** in the internal story panel and in `story-map story`, the JSON export and `story-map diff`. `story-map tokens` works it out per response from the model the log names, at API list prices built in and dated in `defaultTokenPricesDate`, with cache writes priced by duration and fast mode at twice the price. `--prices <file>` replaces the built-in prices. Tokens from models with no price are named and left out of the cost.
- `story-map edit` takes `--tokens <n>` and `--estimated-cost <usd>`, and `--from` takes the `tokens` and `estimated-cost` ops.
- New exports `countStoryTokens`, `branchNamesStory`, `defaultClaudeLogs`, `defaultTokenPrices` and `defaultTokenPricesDate`, and types `StoryTokenOptions`, `StoryTokenUsage`, `TokenCounts`, `TokenCost`, `TokenPrice` and `TokenPrices`.
- The agent instructions from `story-map init` ask agents to record the tokens and estimated cost in the pull request that finishes a story.

### Agent briefs

- New `storyMapBrief(view, { story })` and `storyMapBrief(view, { release })` write a handoff brief for a coding agent from the internal map: a compact Markdown prompt with `<rules>`, `<target>`, `<context>`, `<in_flight>`, `<open_decisions>` and `<done_when>` sections. It lists the targets with their plan, personas and jobs, the delivered stories nearby to reuse, the planned stories nearby not to build yet, the tagged tests and changes that already name each target, draft jobs, missing estimates and plans, and blocked stories, and names the branch to create. Options `mapPath`, `readFirst`, `validateCommand`, `testCommand` and `baseBranch` fit it to the repository. Text from the map is escaped so it cannot close or add a section. A story brief stays under 4 KB and a release brief under 16 KB. Throws a `TypeError` for a customer or filtered view. New exports `storyMapBriefBranch`, `storyBriefMaxBytes`, `releaseBriefMaxBytes`, `briefBranchMaxLength` and `briefBuiltNearbyMaxItems`, and types `StoryMapBriefRequest`, `StoryMapBriefOptions` and `StoryMapBriefDocument`. See [Write a brief for an agent](https://github.com/duncan-m/auto-story-map/blob/main/docs/story-map.md#write-a-brief-for-an-agent).

### Agent brief on the board

- New `brief` option for `getStoryMapForViewer` and `getStoryMapPage`. Pass `true`, or the options of `storyMapBrief`, and each planned, in-progress or blocked story, and each release with planned or in-progress stories, gets its agent brief as `brief` on the internal view. Briefs are written before the filters, so a search does not change them. Off by default, and never on customer views. The JSON export and the CLI's read commands leave `brief` out.
- Internal story and release panels with a brief have an **Agent brief** section, with a closed **Show the brief** block to read and select the brief, and a **Share** menu at the top right in place of **Copy link**. The menu holds **Copy link** and **Copy brief**, which board.js shows and wires up, saying what it copied, such as “Copied brief: ESM-111”. The menu's button says “Copied” after a copy, and Escape closes the menu without closing the panel. Panels without a brief keep the plain **Copy link**. New board.js export `enhanceStoryMapBriefs`, and classes `esm-brief`, `esm-brief-intro`, `esm-brief-details`, `esm-brief-text`, `esm-panel-menu`, `esm-menu-item`, `esm-menu-item-text` and `esm-menu-item-hint`. `story-map preview` and the demo turn briefs on. See [Copy a brief from the board](https://github.com/duncan-m/auto-story-map/blob/main/docs/story-map.md#copy-a-brief-from-the-board).
- New `webAgents` board prop, such as `webAgents={["claude", "chatgpt"]}`, adds **Open in Claude** and **Open in ChatGPT** to each **Share** menu, starting a new web chat with the brief filled in. Off by default, because it sends internal map content to those companies. When the link would be longer than 8,000 characters, it opens an empty chat and board.js copies the brief first. New exports `storyMapWebAgents` and `webAgentLinkMaxLength` and type `StoryMapWebAgent` from `auto-story-map/react`, and class `esm-menu-agent`. The demo turns both on. See [Open a brief in a web agent](https://github.com/duncan-m/auto-story-map/blob/main/docs/story-map.md#open-a-brief-in-a-web-agent).
- `webAgents` takes `"claude-code"`, which adds **Open in Claude Code** to each **Share** menu. It starts a new Claude Code session on the web, at `https://claude.ai/code`, with the brief filled in, in the repository from `repositoryUrl` when that is a GitHub address, passed as `repo=<owner>/<name>`. Anthropic does not document these parameters, so if they change, the link opens Claude Code without the prompt or repository. New type `StoryMapWebAgentInfo`, and `storyMapWebAgents` entries gain `opens` and `repository`. The demo turns it on. See [Open a brief in a web agent](https://github.com/duncan-m/auto-story-map/blob/main/docs/story-map.md#open-a-brief-in-a-web-agent).

### Story dependencies

- Stories can list the stories they depend on in a new optional `dependsOn`, up to 10 story IDs. Validation rejects unknown, repeated and self dependencies and cycles, and warns when a story depends on a cut story. See [Record dependencies](https://github.com/duncan-m/auto-story-map/blob/main/docs/story-map.md#record-dependencies).
- Internal cards show how many stories they depend on, to the right of the status, counting only those not yet merged or shipped, so a card whose dependencies are all delivered shows no count. The story panel counts every dependency and shows a Dependencies section listing the stories it depends on and the stories waiting for it, with their status and release, each opening its panel. Customers never see dependencies.
- Internal views give each story `dependsOn` and `dependents`, each a list of `StoryDependency` with the story's ID, title, status and release, so they stay complete when a filter hides those stories. The JSON export and `story-map story` include them. New export `storyDependsOnMaxItems`.
- `story-map edit` takes `--add-dependency` and `--remove-dependency`, `story-map add` takes `--dependency`, and `--from` takes the `add-dependency` and `remove-dependency` ops and `dependsOn` on `add`. `story-map diff` shows dependencies added and removed.

### Read and change the map from the command line

- New `story-map story <ID> [...]`, `story-map stories` and `story-map releases` read the map from the command line as text, or as JSON with `--format json`, so agents stop reading the YAML by hand. `stories` takes the board's filters: `--status` (with `stalled` and `all`), `--release`, `--activity`, `--query` and `--changed-within`, and hides blocked and cut stories unless asked, as the board does. All three take `--map`, `--history` and `--tests-index`. JSON stories have the same shape as the JSON export. An unknown story ID exits 1 and suggests close matches. New exports `findStories` and `getStories`, and types `StoryQuery`, `FoundStories` and `MissingStory`. See [Read the map from the command line](https://github.com/duncan-m/auto-story-map/blob/main/docs/story-map.md#read-the-map-from-the-command-line).
- `story-map validate --format json` prints each map's result and every issue with its severity, file, line, column, YAML path, readable target, item ID and message. Exit codes are unchanged. New export `checkStoryMap`, which returns the same result without printing, and types `StoryMapCheckResult`, `StoryMapCheckIssue` and `StoryMapCheckOptions`.
- New `story-map edit <ID>`, `story-map add` and `story-map release-impact <release ID>` change the map as named edits, so agents stop editing the YAML by hand. `edit` sets `--status` (with `--reason` for blocked and cut), `--release`, `--activity`, `--title`, `--summary`, `--notes`, `--add-source`, `--remove-source` and, with `--customer`, customer copy. `--from <file>` applies a JSON list of edits, all or none. Each is a dry run that prints the YAML line diff, the `story-map diff` summary and the problems the edit introduces, until `--write`, which saves only a valid map. Comments and every untouched line are kept byte for byte. There is no delete, `release-impact` always adds `draft: true`, `add` never reuses an ID, and `--updated-by` is needed to set `updatedBy`. New exports `proposeStoryMapEdit`, `nextStoryId`, `StoryMapEditError` and `storyMapEditOperationSchema`, and types `StoryMapEditOperation`, `StoryMapEditOptions` and `StoryMapEditResult`. See [Change the map from the command line](https://github.com/duncan-m/auto-story-map/blob/main/docs/story-map.md#change-the-map-from-the-command-line).
- `story-map add` numbers a new story one after the highest ID in the map, such as BILLING-205 after BILLING-204, whatever its release, and takes `--id` to choose one. `nextStoryId(stories)` does the same, and ignores its optional `release` argument. Existing IDs never change. See [Change the map from the command line](https://github.com/duncan-m/auto-story-map/blob/main/docs/story-map.md#change-the-map-from-the-command-line).
- New `story-map preview [<map.yaml>]` serves the map as a board on `http://127.0.0.1:4173/story-map`, with internal and signed-in customer views, the JSON view and the export menu, so a team can check its map before adding the board to its product. It reads the map on every request and shows validation errors on the page. It listens on loopback only, refuses requests addressed to any other host, and takes `--port`, `--history`, `--tests-index` and `--source-base-url`. It needs `react` and `react-dom`, now listed as an optional peer dependency. See [Preview the map locally](https://github.com/duncan-m/auto-story-map/blob/main/docs/story-map.md#preview-the-map-locally).
- New `story-map help <command>` prints just that command's options. A usage error now prints the usage for the command that was run, instead of every command's.

### Estimates

- Stories can carry an optional `estimate` in story points: 1, 2, 3, 5, 8 or 13. Any other value is a validation error. New exports `estimatePoints` and type `EstimatePoints`. Existing maps stay valid.
- Validation warns about a `planned` or `in-progress` story with no estimate, but only in a release where another story has one, so maps that do not use estimates get no new warnings. `--strict` makes it fail.
- Internal views carry each story's `estimate`, and each release's `estimates`: `{ total, merged, left, unestimated }`. Cut stories are left out, `merged` counts the points on merged stories, `left` counts only stories that are not merged or shipped, so a release whose work is all merged has 0 left, and the totals count the whole release whatever the filters. Releases with no estimated story have no `estimates`. Customers never see either. New type `ReleaseEstimates`. See [Estimate effort](https://github.com/duncan-m/auto-story-map/blob/main/docs/story-map.md#estimate-effort).
- Internal boards show estimates. A card shows its estimate at the top right, such as “5 pts”. ## 0.6.1

There is no 0.6.0 release. 0.6.1 follows 0.5.0.

No upgrade steps. Existing maps and history files stay valid. Mainly fixes from a code review of 0.5.0, several of them security fixes, plus new exports and a new board header.

- `getStoryMapForViewer` and `getStoryMapPage` group history events in linear time. They used to copy each story's growing list for every event, so a history with many events for one story took quadratic time: 100,000 events took over a minute and now take well under a second. Entry order is unchanged, including for events with the same timestamp.
- With history, the internal board's header says when the map was last updated and by whom, and which releases recent changes focused on, such as “Last updated 4 hours ago by Sam Patel. Recent changes focused on 0.6.1 (12 stories) and 0.5.0 (3 stories).” It replaces the map's `summary` there. Without history, and for customers, the header still shows the summary. Internal views carry the data in a new `recentUpdates` field. New export `recentUpdateDays` and type `StoryMapRecentUpdates`.
- `story-map init` titles the starter map “[App Name] Story Map”, such as “Field Ops Story Map”, instead of “Field ops story map”.
- Activity titles on the board are larger: `.esm-activity-title` is now `1.1rem`.
- `story-map history` and `story-map diff` read past versions of the map leniently, so a future format change that removes or renames a field or status no longer breaks them. Fields the format no longer has are ignored, and a story that no longer validates is left out of that version only. History used to skip every such version silently, losing its events and dates, and diff failed until the change merged.
- History now records each version it cannot read, because the map was missing or not valid YAML, in new optional `skipped` and `skippedCount` fields, and `story-map history` warns about them and still exits 0. `parseStoryMapHistory` accepts files with and without these fields. New type `SkippedStoryMapVersion`.
- When the diff's base drops anything, the summary starts with a note saying what, and `--format json` adds `baseDropped`.
- `story-map history` fits names to the history format, so `parseStoryMapHistory` always accepts the file it writes. Git author and committer names have no length limit, and a name over 120 characters used to produce a history file that failed to load. Names are trimmed and cut to 120 characters ending in “…”, and blocked or cut reasons to 500, counting characters rather than UTF-16 code units so emoji are never split. `parseStoryMapHistory` counts the same way, so it now accepts names of up to 120 emoji.
- New `getStoryMapPage(document, viewer, { canViewInternal, history, stalledAfterWeeks, now, searchParams })` projects the map for the viewer and then applies the filters from `searchParams`, so the safe order is the easy one. It returns the same as `filterStoryMapView(getStoryMapForViewer(...), readStoryMapFilters(searchParams), { now })`, which remain available. New type `StoryMapPageOptions`.
- New `storyMapResponseHeaders`: `Cache-Control: private, no-store` and `X-Content-Type-Options: nosniff`, for every story map response.
- The example host and the integration guide use both. The guide has a new [Large maps](https://github.com/duncan-m/auto-story-map/blob/main/docs/story-map.md#large-maps) section with measured page sizes.
- CLI options no longer take the next option as their value. `story-map validate --plans --strict map.yaml` and `story-map history --map --allow-shallow` used to read `--strict` and `--allow-shallow` as paths. They now print `story-map: --plans needs a value` and the usage, and exit 2. Pass a value that starts with a hyphen as `--name=-value`. The same applies to `init --dir`.
- `--check-sources` and `--plans` no longer follow symbolic links out of the repository. A source or plan file that links outside is reported as pointing outside the repository through a symbolic link, and is not read. Links inside the repository still work.
- `--check-sources` reads heading anchors in linear time, so a Markdown heading full of unclosed `<`, `[` or trailing spaces can no longer stall validation. A 200 KB heading used to take about 14 seconds. Heading anchors are not checked in Markdown files over 5 MB, and the source is reported instead.
- `story-map diff` escapes `@` and `#` in text from the map, so pasting the summary into a PR does not mention people or teams, or link issues.
- `StoryMapBoard` no longer fails to render when given a `locale` or `timeZone` the runtime does not recognise, such as `timeZone="Nowhere/Nope"`. It uses `en-GB` or the server's time zone instead, and logs a warning once. The board also builds its date formatters once per render instead of once per date. Rendered markup is otherwise unchanged.
- `story-map init` no longer follows symbolic links out of the host repository. A link at `AGENTS.md`, the map, the guide or the workflow that points outside the chosen directory, or is broken, is refused with a message instead of being written through. It skips a read-only `AGENTS.md` that already has the story map section, and accepts in-repository names that start with two dots, such as `..docs`.
- Text output from `story-map validate` escapes line breaks and control characters in messages and paths, so map text cannot add lines that look like other diagnostics or send terminal escape codes.
- Validation locates problems in linear time. A map with many unknown or duplicate fields used to make validation quadratic.
- The diff's note about stories dropped from an older-format base shows each rejected ID as inline code, so an ID with backticks, links, mentions or line breaks cannot change the summary.
- The release workflow checks that the packed `package.json` matches the committed one and pins the npm registry, so a tampered tarball cannot redirect the publish.

- Story panels show “Last updated 3 days ago by Sam Patel” from the last edit, and fall back to `updatedBy` without it. Status changes and the **Changed** filter are unaffected.
- Edits authored by bots are credited to whoever merged them, in both the last edit and status history. Names ending in `[bot]` are bots. New `--bot-names` option on `story-map history`, and `botNames` on `buildStoryMapHistory`.
- `updatedBy` is now optional guidance. The guide and the `AGENTS.md` template ask agents to set it only when the commit author is not the person to credit.

### Validation

- Validation issues have a `severity` of `error` or `warning`. Warnings do not make a map invalid. The first warning is a blocked or cut story with no `statusReason`. New `storyMapWarnings(document)`.
- `story-map validate` prints warnings with `warning:`, emits `::warning` annotations with `--format github` and exits 0 when there are only warnings. Add `--strict` to fail on warnings.

## 0.3.0

Upgrade steps: [Upgrade to 0.3.0](https://github.com/duncan-m/auto-story-map/blob/main/docs/story-map.md#upgrade-to-030). The YAML format is unchanged.

### Board

- **Breaking:** the board is now a grid of activity tiles and coloured release lanes, with a story count per release. The markup and class names changed, so remove host CSS that targets `.esm-table`, `.esm-card-toggle` or `<details>`.
- Cards show only the story ID, title and status. Selecting a card opens a detail panel with the summary, activity and release. For internal viewers, the panel also shows the engineering overview, notes, linked sources and last editor. The panel uses the popover API and works without client-side JavaScript.
- New `filterStoryMapView` and `readStoryMapFilters` add a search box and status filter, submitted as a GET form. Use `preservedParams` to keep the host page’s own query parameters.
- New `theme` prop: `light` (default), `dark` or `auto`. All colours are `--esm-*` custom properties.
- Phones show each release lane as a stacked section.
- Engineering overview and source links in the story panel open in a new tab, with an icon and screen-reader text that say so.

### Access and validation

- New `canViewInternal` option on `getStoryMapForViewer` lets the host decide who sees the internal map. The default is unchanged: the `engineer` and `super-admin` roles.
- `parseStoryMap` throws `StoryMapValidationError`. Its `issues` give the path, message, line, column and containing item ID. Every problem is reported in one run, including reference checks when another field is invalid.
- `story-map validate` prints `file:line:column` and supports `--format github` for PR annotations.
- New `--check-sources` validator option checks that repository-relative sources exist and that Markdown `#heading` links match a heading. New `--plans <folder>` checks that story IDs mentioned in delivery plans exist in the map.
- The package ships `story-map.schema.json` (also exported as `auto-story-map/schema.json`) for editor autocomplete and inline checks.
- **Breaking:** `storyMapSchema` is now a Zod 4 schema.

### Reviewing changes

- New `story-map diff <base-ref>` prints a Markdown summary of a map change for the PR, starting with what signed-in customers will see. `diffStoryMaps` and `formatStoryMapDiff` expose the same comparison in code.

### Status history

- New `story-map history` reads the map’s Git history and records when each story was added and each status change, who made it and who merged it. Pass the result to `getStoryMapForViewer` as `history`.
- Internal cards show the time since the last change, such as “Shipped · 2 days ago”, and the story panel lists the full history. A new **Changed** filter shows stories added or changed in the last 1, 7, 14 or 30 days (`changed=7d`). The customer view never includes history.
- New `locale`, `timeZone` and `now` props on `StoryMapBoard`, and a `now` option on `filterStoryMapView`.

### Setup

- New `story-map init` command creates a starter map, the story map guide, an `AGENTS.md` section and a GitHub Actions workflow that validates the map and its sources and adds the change summary to each PR. It never overwrites existing files.
